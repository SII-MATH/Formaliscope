## 先定义数学审阅边界

KIP126 已有分类和冻结文档，应以这些为主要依据，而非按所有声明或仅按目录派发：

- `docs/MAC_T_INPUT_AUDIT.md`：区分模型 M、Challenge 交付接口、A(M) 文献输入、C(M) 计算解释、论文推导与最终目标 T(M)。该文档也说明此前轨迹有更新，当前状态还要与各冻结文档一起核对。
- `docs/M_INPUT_FREEZE.md` 与 `docs/A_INPUT_FREEZE.md`：核对所选路线当前模型和文献输入签名。不能把接口已冻结解释成对象、外部结果或最终证明已完成。
- `blueprint/src/chapters/external_results.tex`、`computed_inputs.tex`：精确输入陈述和源文定位，供带意图的审计阶段使用。

拟定三类集合：

1. **必须审阅的数学对象**：主目标、决定其含义的关键定义/实例、文献输入签名及应用条件、计算结果的数学解释、模型/表示运输和关键论文推导接口。
2. **为这些对象提供上下文的代码**：基础类型、一般引理、辅助定义和实例。可由 Agent 检索、按需展开；不自动生成逐条人工打卡任务。若出现实际语义疑点，再提升到审阅对象。
3. **可浏览的完整索引**：仍保留全库检索与源码，不因此触发 Agent 调用或人工审核要求。

定义与模型绑定在这里非常重要：不能以“只是 def”“已经编译通过”“在 KIPBase”作为免审理由。另一方面，证明相关辅助引理也不应仅因存在就变为人工必审条目。

## Agent 按数学主题组工作

修订方向：一个 Agent 角色，工作单元为语义相关的一组对象，每组每阶段使用独立上下文。组内共享 Lean 定义和实例，结果仍按声明独立记录。

第一个主题组可含以下四条核心声明，其他声明作为按需上下文：

- `KIP126.Solution.Final.H6SquarePermanent.h6_sq_permanent`
- `KIP126.Classical.Adams.sphereAdamsData`
- `KIP126.Classical.Adams.standardH6Square`
- `KIP126.Core.SpectralSequence.NonzeroSurvival`

其他候选主题：所选模型/实例绑定、A(M) 的文献输入、C(M) 的解码与认证边界、classical/synthetic 比较、关键规范化推导。具体成员要先核对冻结文档及 Lean 语义上下文，不在这份修订中随意宣称完整。

Workflow 负责：

- 明确 review_targets 与 context_only，去重共享上下文，保持目标与证据对应。
- 根据上下文长度和数学关联拆组，不按“每条一个进程”的固定规则，也不把全库塞入同一上下文。
- 第一阶段仅给 Lean 上下文，逐条产生回译及覆盖记录；第二阶段开启新上下文，加原始意图核对，再做分级。
- 对含糊、遗漏或高风险条目追加单独深入任务；其余组内处理即可。
- 保留每条结果的版本、证据和人工判断，避免一个组结论掩盖其中某条的错误。

同组共享上下文的效果要用试运行检查，特别是模型会不会用邻近声明补出当前声明没有的前提或结论。组大小按实际上下文预算决定，暂不承诺固定条数或节省比例。
